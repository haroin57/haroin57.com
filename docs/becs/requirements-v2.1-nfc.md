# 生活ハードコード化システム 要件定義書 v2.1 — NFC Edition

**Behavioral Environment Control System（BECS）**  
**版:** 2.1 / NFC Edition・改訂ドラフト  
**作成日:** 2026-11-17  
**対象:** 個人利用・本人が管理権限を持つデバイスおよび生活環境  
**改訂元:** v2.0『生活ハードコード化システム 要件定義書』および原案『低レイヤー制御統合版 生活ハードコード化システム要件定義書』

> **本書の位置づけ**  
> v2.0の「状態管理→ポリシー計算→デバイス適用」「安全な解除」「生活ルーティン」を維持し、**BLE/iBeaconによる空間検知を廃止して、iPhoneによるNFCタッチを主たる生活チェックポイントに変更**する。NFCは意図的な操作の記録であり、位置や筋トレ実績を暗号学的に証明する手段ではない。センサーを完全排除するのではなく、エアロバイクのRPM測定など、物理計測が必要な箇所は維持する。数値・設定は初期案であり、iOSバージョンと実機で動作を確認する。

## 0. エグゼクティブサマリー

### 0.1 目的

生活の各フェーズ（起床、出発、研究、休憩、筋トレ、エアロバイク、日次クローズ）を**生活空間に設置したNFCタグへの明示的なタッチ**で進める。タグ読み取りから生成されたイベントを中央のState Reducerが検証・確定し、Policy EngineがmacOS、DNS、視聴環境、照明等に適用するポリシーを計算する。タッチの手間を小さくしつつ、行動開始・終了を本人が意識して宣言できるようにする。

### 0.2 設計原則

1. **NFCは意図的なチェックポイント。** タグに触れたという操作を行動の申告として扱い、無接触の在室・退出・滞在時間は推定しない。
2. **NFCは認証鍵ではない。** タグのUIDやURLは複製・転記され得る。本人認証、デバイス認証、権限判定はバックエンドで実施する。
3. **制御判断は中央のPolicy Engine。** タグやショートカットからデバイスを直接ロック・通電せず、イベント受理→状態遷移→ポリシー配布で一元化する。
4. **タッチと達成を区別する。** タグは筋トレ完了や入浴完了の自己申告を記録できるが、肉体行動の客観的な証拠とはみなさない。25分集中とバイクRPMは別の計測で検証する。
5. **タグやiPhoneが故障しても生活を止めない。** PWAの手動操作、オフラインPC解除、休養・緊急時の例外経路を維持する。
6. **本人が管理する環境のみ対象。** 緊急連絡、医療、防災、仕事、認証、交通、休養を遮断しない。危険な電源操作を要求しない。

### 0.3 v2.0→v2.1の変更点

| 項目 | v2.0 | v2.1 NFC Edition |
|---|---|---|
| 生活チェックポイント | BLE/iBeacon・Wi-Fiからの滞在候補 | **iPhoneのNFCタッチによる明示イベント** |
| iOSの初期実装 | ネイティブBLE背景観測の検証 | **ショートカットのNFCオートメーション**を第一候補にする |
| 読み取り代替 | BLE未検知時に手動確認 | タッチ不能時はPWAボタン、NDEF URL方式を代替経路にする |
| タグ管理 | `NODE_WASHROOM`等のBLEノード | `nfc_tags`/`nfc_bindings`で登録・設置・停止・交換を管理 |
| セキュリティ | デバイス資格情報・イベント署名 | 加えて**NFCの複製・貼替・URL再訪・再タッチの区別**を設計 |
| 行動の真偽 | 観測と確定を区別 | **本人によるNFC操作の申告**と物理的証明を区別 |
| エアロバイク | ESP32でRPM判定 | **変更なし**。NFCはセッション開始、RPMはESP32で検出 |
| 安全・解除 | 期限付きポリシーと緊急解除 | **変更なし**。NFCタグを解除の必須条件にしない |

### 0.4 採用する読み取り方式

- **第一候補（MVP）：iOSショートカットNFCオートメーション。** 各タグを端末側のオートメーションに紐付け、タッチをトリガーに特定のアクションをAPIへ通知する。Appleによると、このトリガーはタグの固有識別子を使い、**タグ内部のNDEF内容は参照しない**。自動実行可能かはOS・設定・実行アクションを実機で検証する。
- **代替（クロスデバイス）：NDEF URLタグ。** `https://<BECSホスト>/tap/<公開tag_id>` をタグへ書き込み、iPhoneの背景タグ検出から通知をタップしてWeb画面を開く。Appleの背景読み取りでは通知タップや必要時のロック解除を要する。**URLへのGETアクセスでは行動を確定せず、本人認証後のPOSTで確定**する。
- 初期MVPでMDMやネイティブNFCアプリを必須としない。ショートカット方式の可用性が不十分なら専用iOSアプリ/App Intentsを追加検討する。

## 1. スコープと成功条件

### 1.1 対象範囲

- 朝45分以内の出発、研究25分集中・90分ごとの休憩、帰宅後の筋トレ3セット、エアロバイク24〜48分、入浴、クロッキー、翌日To-DoとX投稿案という既存ルーティン。
- 洗面所、玄関、研究室、研究机、筋トレスペース、バイク、入浴前、クロッキー机、就寝場所のNFCチェックポイント。
- iPhoneのショートカットNFCオートメーション、NDEF URL方式、PWA手動ボタン。
- NFCタグの登録・紐付け・無効化・交換、タッチ履歴、状態遷移の承認・却下・訂正。
- Next.js/PWA、中央状態管理、Policy Engine、macOS LaunchAgent、NextDNS/Pi-hole、ESP32のバイクRPM計測。
- iOSのアプリ制限/MDMは後期の任意検証フェーズ。

### 1.2 対象外・禁止事項

- NFCタッチなしでの**在室継続・自動退出・所要時間の自動証明**。継続時間はタイマー/実測機器から得る。
- NFCタグ・UID・タグ内URLをアクセス権限の秘密情報として扱うこと。
- タグ紛失、iPhone故障、サーバー断で解除できなくなる永久ロック。
- 生活必需通信・緊急連絡の遮断、危険な電源操作、AC100V自作リレーの必須化。
- 非対応のiOS背景実行を保証したり、NFCタッチで本人の生体的行動を証明したりすること。
- Xへの無確認投稿、第三者端末への無断制御。

### 1.3 成功指標（前後比較）

| 指標 | 定義 | 計測・評価 |
|---|---|---|
| 朝の出発達成率 | 起床NFC確定から45分以内の外出NFC確定率 | `NFC_WAKE`→`NFC_DEPARTURE`の受理時刻 |
| 研究開始遅延 | 研究室到着NFC→最初の集中開始までの時間 | チェックポイントとセッション開始の差 |
| 25分集中達成率 | 途中中断を除き実際に25分のタイマーを完了 | セッションサーバー/PC Agent |
| 90分ごとの休憩 | 累積90分の研究後に休憩を取った割合 | 集中セッション累積時間 |
| 夜ルーティン達成率 | セット3回・バイク実測・入浴・クロッキー・日次クローズの達成 | NFC自己申告＋RPM計測＋タスク履歴 |
| NFC運用品質 | 読取成功率、誤登録、連続タッチ、通知/実行遅延 | `nfc_scan_attempts` と実機試験 |
| 制御の信頼性 | 反映失敗・不意のロック・手動解除・復旧時間 | ACK/監査ログ |
| 主観的負担 | タッチによる追加手間、制限が役立つか | 週次の短い自己評価 |

**評価原則:** 成功率のために過剰な制限を課さない。タグのタッチ忘れは即座に「行動しなかった」とは判断せず、遡及的な手動訂正を許容する。

## 2. ユースケースと生活ルーティン

### UC-01 朝の起床と出発

1. 予定起床30分前に、メーカーが自動運転を許容する空調・照明だけを安全に起動する。**この時間トリガーはNFCとは独立**。
2. 洗面所の `NFC_WAKE` タグをiPhoneでタッチする。受理後 `routinePhase=MORNING` となり45分カウントを開始。朝のSNS/娯楽を制限し学習/連絡機能を許可する。
3. 玄関の**外出専用** `NFC_DEPARTURE` をタッチする。受理後 `TRANSIT` に移り出発時刻を記録する。
4. 朝45分を超えてもペナルティで機器をロックしない。タッチ忘れは手動で補正できる。

### UC-02 研究室と集中

1. 研究室入口の `NFC_LAB_ARRIVAL` をタッチし、到着を申告する。受理後 `RESEARCH` とし、macOS Agentがエディタと`/focus`を起動する。
2. 研究机の `NFC_FOCUS_START` をタッチするかPWAで開始する。25分集中の計測は**タイマー側**が行う。
3. タグを2回続けてタッチしても新規集中セッションが重複開始されない。同じタグを次のセッション開始に再利用できる。
4. 25分の実計測が完了したときだけ最大15分の娯楽解放権を付与。NFCタッチや単なる経過だけで付与しない。
5. 研究累積90分に達したら10分休憩を案内する。休憩中も`routinePhase=RESEARCH`を維持する。

### UC-03 帰宅、筋トレ、エアロバイク

1. 玄関の**帰宅専用** `NFC_HOME_RETURN` をタッチする。研究フェーズが終了し、夜ルーティンを提示する。休養日/外出継続を本人が選択できる。
2. `NFC_STRENGTH_SET` を**実際に1セットを終えるごとに1回**タッチする。各タッチは別の`scan_id`とセット番号を持ち、3回まで加算。短時間の誤タッチや重複送信を区別する。
3. 筋トレ3セットを記録すると、バイクでの動画視聴資格を付与する。セットタッチは完了の自己申告であり、フォーム・運動強度の証明ではない。
4. バイクの`NFC_BIKE_START`をタッチしてセッションを開始。**RPMの計測、5秒停止警告、10秒で再生一時停止はESP32がローカルで実施**する。
5. バイク終了はESP32/プレイヤーまたはPWAで確定する。安全・体調上の理由で中断可能。目安24〜48分。

### UC-04 入浴・クロッキー・日次クローズ

1. 洗面所など水濡れの少ない安全な位置に置いた`NFC_BATH_DONE`で入浴完了を自己申告する。
2. クロッキー机の`NFC_CROQUIS_DONE`で完了を記録する。
3. 机の`NFC_DAILY_CLOSE`で日次クローズ画面を開き、当日レビューと翌日の優先To-Doを3枠確認する。条件を満たしている場合だけクローズを確定する。
4. 日次ヒートマップとX投稿案を生成する。投稿は本人承認が必須。
5. 就寝場所の`NFC_SLEEP`で就寝準備へ切り替える。端末の緊急連絡やOS復旧機能は制限しない。

### UC-05 タグを忘れた・使えない場合

- タッチができない場合、PWAの**手動チェックポイント実行**から同じ状態遷移を実行できる。手動経由は監査ログに区別して残す。
- タグ紛失/貼り替え時は旧タグを無効化し、新しい`tag_id`を登録し直す。過去イベントの参照を維持する。
- サーバー不通時、ショートカットが端末内キューを持たないなら自動再送・成功表示をしない。PWAには未送信/未確認を表示する。再同期時は古いタッチを状態遷移に無条件適用しない。

## 3. 全体アーキテクチャ

### 3.1 論理構成

```text
 ┌─────────────────────────────────────────────────────────┐
 │ 生活空間のNFCタグ                                       │
 │ 洗面所 / 玄関(外出・帰宅) / 研究室 / 机 / 筋トレ / ...      │
 └─────────────┬──────────────────────────┬────────────────┘
               │ NFCタッチ                 │ NDEF URL 読取
    ┌──────────▼──────────┐   ┌──────────▼───────────────┐
    │ iPhone ショートカット │   │ iPhoneブラウザ / PWA       │
    │ NFCトリガー→API POST  │   │ GET /tap/:tagId →確認POST  │
    └──────────┬──────────┘   └──────────┬───────────────┘
               └──────────────┬───────────┘
                              │ 認証された操作
                    ┌─────────▼──────────────────────────┐
                    │ Control Plane                     │
                    │ NFC Scan Ingestion / Tag Resolver │
                    │        ↓                           │
                    │ State Reducer / State Machine     │
                    │        ↓                           │
                    │ Policy Engine                     │
                    │        ↓                           │
                    │ Command Dispatcher / Outbox       │
                    │ PostgreSQL / Audit / Scheduler    │
                    └─────────┬──────────────────────────┘
                              │ revision / 期限 / ACK
                   ┌──────────▼─────────────────────────┐
                   │ macOS Agent / DNS / iOS(任意) /     │
                   │ 対応照明・空調 / 動画再生クライアント │
                   └────────────────────────────────────┘

  別経路: ESP32 Bike Controller → RPM/停止判定をローカルで実行
  独立経路: PWA手動操作、オフラインPC緊急解除、機器安全停止
```

### 3.2 コンポーネント責務

| コンポーネント | 主責務 | 責務外 |
|---|---|---|
| NFC Tag Registry | タグ登録・設置場所・用途・有効状態・交換履歴 | 認証秘密の保持 |
| iOS Shortcuts NFC Bridge | タグ別の自動化を起動し、スコープ付き端末認証でイベント送信 | タグから管理者権限を得ること |
| NDEF Web Landing | タグURLから本人向け確認画面を表示 | GETアクセスだけで行動を確定すること |
| NFC Scan Ingestion | 端末/ユーザー認証、`scan_id`冪等性、タグ有効性、レート制御 | 無検証で直接ロック/解除 |
| Tag Action Resolver | 有効なタグをバージョン付きアクションに解決 | クライアントの`action_type`を信頼すること |
| State Reducer | 現状態に対する遷移受理/拒否、変更履歴 | 複製タグから在室を客観的に確定 |
| Policy Engine | 状態から安全・例外優先の方針を計算 | 個々のNFC APIに結合すること |
| Dispatcher | revision/期限/ACK付きで制御を配布 | 配布要求を適用成功と誤認すること |
| PC Agent / DNS / MDM | 対象デバイスへのポリシー適用 | 緊急連絡・生活必需の遮断 |
| ESP32 Bike Controller | RPM計測・停止判定・動画制御 | NFCタッチをRPMとみなすこと |
| PWA | 状態表示、タグ管理、手動操作、訂正、解除 | 非対応のブラウザ背景NFCを前提にすること |

### 3.3 技術スタック

- Web：Next.js + TypeScript + PWA。認証済みダッシュボードと`/tap/[tagId]`を提供する。
- API：TypeScriptでNFC受付、リデューサー、Policy Engine、Dispatcherを実装。DBはPostgreSQL、キュー/時刻ジョブはWebのリクエスト処理から独立。
- NFC：iPhoneショートカットのNFCトリガーをMVPの標準とする。任意でNDEF URL方式を用意し、将来App Intents/専用iOSアプリを検討。
- NFCタグ：再書込可能な**NDEF対応13.56MHzタグ**を評価対象とする。ショートカット方式ではタグのNDEF書込は不要な場合がある。耐水・設置材質（金属面への貼付など）は実物で確認する。
- PC：macOS User LaunchAgent/Hammerspoon。必要な特権操作のみ最小権限Helper。
- DNS：NextDNS専用プロファイルを第一候補。必要ならPi-hole/OSファイアウォールを組み合わせる。
- バイク：ESP32＋ホール/リードセンサー＋再生クライアント。RPM/停止判定はローカル。
- iOS MDM：NFC読み取りの前提条件にはしない。後期の任意研究対象。

## 4. ドメインモデルと状態遷移

### 4.1 直交状態とNFC入力モデル

```typescript
type Location = "HOME" | "TRANSIT" | "LAB" | "OUTSIDE" | "UNKNOWN";
type LocationEvidence = "NFC_SELF_DECLARED" | "MANUAL" | "UNVERIFIED";

type RoutinePhase =
  | "SLEEPING" | "MORNING" | "TRANSIT" | "RESEARCH"
  | "EVENING_STRENGTH" | "EVENING_BIKE" | "EVENING_WRAPUP"
  | "COMPLETED";
type FocusPhase = "IDLE" | "FOCUS_25" | "BREAK_10" | "PAUSED";
type OverrideMode = "NONE" | "TEMPORARY" | "EMERGENCY";

type DailyProgress = {
  morningDepartureWithin45m: boolean | null;
  focusSessionsCompleted: number;
  researchActiveSecondsSinceBreak: number;
  strengthSetsCompleted: number;     // 0..3。完了は本人申告
  bikeActiveSeconds: number;         // ESP32の実測を優先
  bathCompleted: boolean;
  croquisCompleted: boolean;
  tomorrowTop3Defined: boolean;
  dailyReviewCompleted: boolean;
};

type SystemState = {
  location: Location;
  locationEvidence: LocationEvidence;
  routinePhase: RoutinePhase;
  focusPhase: FocusPhase;
  overrideMode: OverrideMode;
  progress: DailyProgress;
  lastCheckpointTagId?: string;
  revision: number;
  updatedAt: string;
};

type NfcScanRequest = {
  scan_id: string;                   // タッチ試行ごとに新規UUID
  tag_id: string;                    // サーバー発行の公開識別子。秘密ではない
  device_id: string;
  source: "IOS_SHORTCUTS" | "NDEF_WEB" | "NATIVE_APP";
  occurred_at: string;
};
```

`Location`は**最後に本人が申告したチェックポイントに基づく生活上の状態**であり、GPS測位や在室証明ではない。`locationEvidence`を持ち、誤解を防ぐ。

### 4.2 入力イベント

| イベント | 入力元 | 確定条件 |
|---|---|---|
| `NFC_SCAN_RECEIVED` | Shortcuts/認証済みWeb/App | 受理試行の記録。**これだけでは状態変更しない** |
| `NFC_CHECKPOINT_ACCEPTED` | Tag Resolver/Reducer | タグ有効・本人認証・フェーズ遷移条件をすべて通過 |
| `NFC_CHECKPOINT_REJECTED` | Tag Resolver/Reducer | 無効/不正なタグ、フェーズ矛盾、レート制限、期限外など |
| `CHECKPOINT_MANUAL_CONFIRMED` | PWA | 明示的な手動操作。NFCと区別して記録 |
| `FOCUS_STARTED` / `FOCUS_COMPLETED` | セッションタイマー/PC Agent | 完了時の実計測25分と中断除外を検証 |
| `BREAK_STARTED` / `BREAK_COMPLETED` | タイマー/本人 | 対象セッションとの対応 |
| `STRENGTH_SET_RECORDED` | NFC/手動 | 同一スキャン再送排除、セット番号の上限確認 |
| `BIKE_SESSION_STARTED` / `BIKE_SESSION_ENDED` | NFC/PWA/ESP32 | 進捗時刻はRPM実測を優先 |
| `BIKE_TELEMETRY` | ESP32 | ローカルのRPM、停止判定、異常 |
| `DAILY_CLOSED` | PWA/Reducer | 日次クローズの条件をサーバーで再検証 |
| `OVERRIDE_STARTED` / `OVERRIDE_ENDED` | PWA/PC Agent | 本人による操作。NFCなしでも実行可 |
| `DEVICE_OFFLINE` / `DEVICE_RECOVERED` | Worker | 制限の縮退と再同期 |

### 4.3 フェーズ遷移マトリクス（初期値）

| 変更前 | 操作 | 変更後 | 主な効果・例外 |
|---|---|---|---|
| `SLEEPING` | `NFC_WAKE` | `MORNING` | 朝45分計測。手動起床も許可 |
| `MORNING` | `NFC_DEPARTURE` | `TRANSIT` | 出発時刻記録。失敗しても生活必需を遮断しない |
| `TRANSIT` | `NFC_LAB_ARRIVAL` | `RESEARCH` | macOS研究環境準備。休日は確認/スキップ可 |
| `RESEARCH` | `NFC_FOCUS_START` | `RESEARCH` | `focusPhase=FOCUS_25`。重複開始禁止 |
| `RESEARCH` / `TRANSIT` | `NFC_HOME_RETURN` | `EVENING_STRENGTH` | 帰宅申告。休養/予定変更を選択可 |
| `EVENING_STRENGTH` | `NFC_STRENGTH_SET`（最大3回） | 同左 | セット完了の自己申告を1件記録 |
| `EVENING_STRENGTH` | `NFC_BIKE_START`（3セット以上） | `EVENING_BIKE` | 視聴権発行。休養/代替時は本人確認フロー |
| `EVENING_BIKE` | バイク終了/安全中断 | `EVENING_WRAPUP` | RPM・運動秒数を保存 |
| `EVENING_WRAPUP` | `NFC_BATH_DONE`、`NFC_CROQUIS_DONE` | 同左 | タスクの自己申告を別々に記録 |
| `EVENING_WRAPUP` | `NFC_DAILY_CLOSE` | `COMPLETED` | 条件不足なら画面で不足項目を表示 |
| `COMPLETED` | `NFC_SLEEP` | `SLEEPING` | 就寝モード。緊急解除は残す |

**注記:** `NFC_FOCUS_START`の再タッチでは25分完了にならない。筋トレセットも同じ`scan_id`の二重処理を防ぎつつ、**本当に別のセットを終えて再タッチする操作は許可**する。`NFC_HOME_RETURN`は玄関の出発タグと分離して、前後状態からの誤推定を減らす。

### 4.4 守るべき不変条件

1. `scan_id`はユニーク。ネットワークの再送で同一スキャンを二重反映しない。
2. タグの`tag_id`とアクション種別の対応は**サーバーの登録情報**が権威を持つ。リクエスト中の`action`を信頼しない。
3. 許可・拒否の結果を含めてイベント化し、**拒否したスキャンでポリシーを変更しない**。
4. NFCはチェックポイントの申告であり、物理位置・在室継続・筋トレ実施の客観証明ではない。
5. サーバー受信時の状態とタグの許可遷移を検証する。遅延・過去イベントで現状態を巻き戻さない。
6. 時刻は`occurred_at`と`received_at`を別に保持。評価・監査にどちらを使ったか記録する。
7. 集中タイマーは別計測、バイクRPMと停止判定はESP32内で完結。
8. タグなしの手動補正、休養、一時解除、緊急解除を継続利用できる。
9. 生活日付は`Asia/Tokyo`を基準とし、日跨ぎのセッションは開始日の`daily_plan`へ帰属する。
10. `state_snapshots.revision`は単調増加、デバイスコマンドは旧revisionなら破棄する。

## 5. Policy Engine 要件

### 5.1 制御レベル

| レベル | 名称 | 動作 |
|---|---|---|
| `OBSERVE` | 観測 | 実際の利用状況を記録し、何も制限しない |
| `NUDGE` | 誘導 | 通知、画面表示、作業環境の自動配置 |
| `RESTRICT` | 制限 | DNSフィルタ、利用しないアプリへのアクセス摩擦 |
| `ENFORCE` | 強制 | 検証済み・可逆的な制限のみ。緊急解除が必須 |

導入初期は `OBSERVE` から始め、各制御対象について誤作動と解除経路を実機試験してから昇格する。

### 5.2 優先順位

1. **身体・火災・電気等の安全:** 危険な自動通電をしない、機器の安全停止を阻害しない。
2. **生活必需・緊急アクセス:** 通話、必要な連絡、医療、防災、交通、本人の復旧経路を常に確保。
3. **緊急解除 (`EMERGENCY`):** 習慣化の制限を即時緩和する。ただし物理的安全制約は解除しない。
4. **一時解除 (`TEMPORARY`):** 理由と期限付きで、指定カテゴリの制限を緩和。
5. **通常の生活ルール:** 朝、研究、運動、休息のポリシー。

### 5.3 ポリシーの基本形

```typescript
type EnforcementLevel = "OBSERVE" | "NUDGE" | "RESTRICT" | "ENFORCE";

type EffectivePolicy = {
  policyId: string;
  revision: number;
  deviceId: string;
  level: EnforcementLevel;
  issuedAt: string;
  expiresAt: string; // 原則短い期限。端末側で期限切れを検知する
  domains: { deny: string[]; allowEssential: string[] };
  apps: { discourage: string[]; terminateOnlyIfSafe: string[] };
  desktop: { openApps: string[]; focusUrl?: string };
  bike: { preStrengthRequired: boolean; playWhenPedaling: boolean };
  override: { allowed: true; localFallbackRequired: true };
};
```

`expiresAt` は**ポリシーそのものの有効期限**であり、タスク達成の証明ではない。時間経過だけで報酬を与えないという原案の原則と、時間切れで自動的に安全な状態に戻すという運用を両立させる。

### 5.4 制御マトリクス（初期案）

| フェーズ | DNS | macOS | iOS（後期PoC） | 物理/視聴 |
|---|---|---|---|---|
| `SLEEPING` | 娯楽を抑制、必須通信を維持 | 通知を抑制 | 就寝用設定 | 安全な照明/空調設定のみ |
| `MORNING` | SNS・娯楽を制限 | 必要なら朝ダッシュボード | 学習・連絡系を優先 | エアコン/照明を起動（対応機器限定） |
| `TRANSIT` | 移動・音声学習に必要な通信を優先 | 制御なし | 地図・連絡・決済を使用可 | 非必須家電のみ安全に停止 |
| `RESEARCH` | 娯楽ドメイン制限、研究/認証基盤は許可 | エディタと `/focus`、通知抑制 | 研究・連絡に必要なアプリを保持 | 研究机の照明のみ |
| `BREAK_10`（集中副状態） | 許可したカテゴリを一定時間緩和 | 休憩を案内 | 変更しない/遅延適用を前提 | ストレッチ等を提案 |
| `EVENING_STRENGTH` | 必要に応じて動画を制限 | 夜ルーティン表示 | 安全な通常利用 | 3セット記録まで視聴権は未付与 |
| `EVENING_BIKE` | 対象配信サービスを必要な範囲で許可 | 専用プレイヤー連携 | 原則変更しない | ESP32の停止判定で動画を一時停止 |
| `COMPLETED` | 翌日の計画に応じて制限 | 日次レビュー終了 | 就寝用設定 | 照明を減光。重要電源は維持 |

### 5.5 報酬・解除ルール

- 研究25分の**タイマーによる実計測完了**後に「15分の娯楽解放権」を付与する。未使用分は原則翌日に持ち越さない。
- 10分休憩は健康維持のための時間であり、SNSの利用許可と同義ではない。娯楽解放権との重複・優先関係はUIで明示する。
- 解除権の**付与条件はイベント**、解除期間の**終了条件は期限**とする。
- 緊急解除は、達成条件を満たしていなくても実行できる。
- 報酬ルールの変更はバージョン管理し、過去の達成状況を後から書き換えない。

---

### 5.6 NFCを起点とする制御の原則

- NFCタグの読み取りそのものは**最終的なアクセス権**ではない。権限・状態遷移・休養モードを評価してから`EffectivePolicy`を再計算する。
- タグ交換・無効化・再登録で過去のポリシーや達成ログが書き換わらないようにする。
- `NFC_DAILY_CLOSE`での実行は日次条件を再検証する。タグに保存されたURLだけで強制クローズしない。
- MDM、DNS、PC制御の適用は非同期で、NFC APIの`accepted`をデバイス適用成功と表示しない。
- `EMERGENCY`/休養の選択はNFCタグより優先し、これらの解除にタッチを要求しない。

## 6. デバイス・アダプター別要件

### 6.1 NFCチェックポイントとタグ管理（主要変更）

#### 6.1.1 タグ配置（初期案）

| `tag_id`の用途名 | 推奨設置場所 | 確定イベント/操作 | 実装上の注意 |
|---|---|---|---|
| `NFC_WAKE` | 洗面所の入口付近 | 起床・朝45分計測開始 | タッチできなければ手動起床 |
| `NFC_DEPARTURE` | 玄関・外出側 | 出発チェックポイント | 帰宅タグと物理的に分離 |
| `NFC_HOME_RETURN` | 玄関・帰宅側 | 帰宅チェックポイント | 休養日を強制しない |
| `NFC_LAB_ARRIVAL` | 研究室入口 | 研究室到着の自己申告 | 研究場所の設置許可を確認 |
| `NFC_FOCUS_START` | 研究机 | 25分集中タイマー開始 | 同一セッションの二重開始禁止 |
| `NFC_STRENGTH_SET` | 筋トレ場所 | 1セット完了申告 | 3回まで。正当な反復タッチは許容 |
| `NFC_BIKE_START` | エアロバイク付近 | セッション開始、視聴資格評価 | 回転計測はESP32が別途実施 |
| `NFC_BATH_DONE` | 入浴場所の乾いた出入口 | 入浴完了申告 | 防水・転倒防止、濡れた手で操作を強制しない |
| `NFC_CROQUIS_DONE` | クロッキー机 | 描画完了申告 | 自己申告として記録 |
| `NFC_DAILY_CLOSE` | 日次レビュー机 | 日次クローズ画面/申請 | 翌日To-Do等の条件を検証 |
| `NFC_SLEEP` | ベッドサイド | 就寝準備開始 | 時間・体調に応じスキップ可能 |

`tag_id`は実データではUUID等の**サーバー発行の不透明な識別子**にする。上表の値は用途名である。物理タグのUIDを本システムのグローバル識別子として使わず、Shortcutsでは端末側の登録情報とサーバー上の`binding_id`を対応させる。

#### 6.1.2 読み取り方式A：iOSショートカット（MVP推奨）

1. iPhoneのショートカットで個人用オートメーション → NFCを選択し、対象タグを読み取って登録する。
2. 対応するショートカットは**タグ用途に固定された`tag_id`を指定**し、`scan_id`を新規発行して`POST /api/v1/nfc/scans`を呼ぶ。
3. ショートカットは`tag_id`を**タグ内容から直接読めると仮定しない**。AppleのNFCオートメーショントリガーはタグ固有識別子を用い、内容を無視するため、`tag_id`との対応は登録時に設定する。
4. 認証は端末別の狭いスコープの認証情報をHTTPSヘッダーに付ける。**URL・NFCタグ自体に秘密鍵や管理者トークンを保存しない**。可能なら資格情報をOSの安全な保存領域に持つ専用App Intents連携を後期採用する。
5. タッチ後は「受理/拒否/保留」の短いフィードバックを表示・通知する。ネットワーク失敗を成功扱いしない。
6. 「確認なしで実行」を許容するOS設定は実機で検証する。ロック状態、画面状態、Wallet/カメラ利用時、機種・OSによる制限を受け得るため**完全無操作・100%即時実行は保証しない**。
7. オートメーションの登録は端末ごとに必要。iPhone機種変更時の再設定・紐付け停止を用意する。

#### 6.1.3 読み取り方式B：NDEF URL→PWA（代替）

- NDEF対応タグに`https://<BECSドメイン>/tap/<tag_id>`をURIレコードとして記録する。
- iPhoneで背景タグ読み取りが可能な場合も、通知タップや必要なロック解除が発生し得る。すべての状態で自動遷移するとは仮定しない。
- **`GET /tap/:tag_id`は確認画面の表示のみ**。状態更新は認証済みの`POST /api/v1/nfc/scans`から実行する。リンクのプレビュー、ブラウザ先読み、履歴からの再アクセスで誤実行しない。
- タグ内の`tag_id`は公開情報であり、コピー可能。本人認証とCSRF対策、状態判定を行う。
- NFCをサポートしない端末は同じ画面から手動チェックポイントを実行できる。

#### 6.1.4 タグのライフサイクルと運用

- `DRAFT → ACTIVE → DISABLED → REPLACED`を管理状態とする。交換時は旧IDの再利用を禁止する。
- タグ登録UIで用途、設置場所、写真（任意）、台帳名、方式、接続するiPhone、紐付け状態を確認する。
- 物理タグには「洗面所：起床」「玄関：外出」など**人間が読めるラベル**を併記する。
- 同じ動作に複数タグを紐付け可能にするが、別動作のタグを混同しない。
- タグ故障・貼替・複製疑い時は`DISABLED`へ変更し、使用履歴を保持したまま交換できる。
- 金属面への貼付、耐水、手袋・ケース越しの読取、iPhoneの保持位置などを設置ごとに実機評価する。
- タッチ忘れはPWA手動補正で処理可能。後から投稿された過去のタッチを安易に現在のフェーズへ適用しない。

#### 6.1.5 タッチの正当性と誤操作防止

- NFCは**便利な操作インターフェース**であり、位置証明・不正防止の完全な対策ではない。
- `scan_id`による冪等性と、同一タグ/端末の短い再タッチ抑止（初期案2秒、実測調整）を分けて実装する。
- 筋トレのような意図的反復タッチは、前回受理済みセット番号やセッション状態を利用して適法な次回申告として受け付ける。単純な「同じタグは1日1回」にしない。
- 不整合な時刻・フェーズ・不活性タグ・認証失敗を拒否し、理由を表示する。過度な失敗があれば通知する。
- 解除・緊急処置はタグの存在に依存させず、NFC URLアクセスに特権昇格の効果を持たせない。

**実機検証:** 各主要タグにつき画面ON/ロック中/通信断/ケース装着などを含め100回程度の操作を試行し、トリガー成功率、API受理率、所要時間、誤操作、再設定工数を記録する。方式AとBは別々に測定する。

### 6.2 ESP32：エアロバイク制御

**構成**: ESP32 + ホールセンサーまたはリードスイッチ + 磁石 + ローカル警告手段 + ネットワーク（任意） + 動画再生クライアントへの制御手段。

**ローカル制御要件**

- GPIO割り込み等でクランク回転パルスを取得し、チャタリング除去後にRPMを計算する。
- `50 rpm` を再生開始の初期閾値とする。例：3秒安定して達したら `PEDALING` を確定。
- 再生中は検知揺れを考慮し、例として45rpmを維持閾値とする。実測によって調整する。
- 停止に相当する低RPMが5秒続けば警告、10秒続けば `PAUSED` に遷移する。この**判定はESP32内で完結**する。
- 明らかに低いペースが続くケースは、別途設定可能な猶予時間のあと再生一時停止とする。急な停止と低ペースを同じ判定にしない。
- サーバーが不通でもRPM計測・停止判定・ローカル停止操作を継続する。
- 筋トレ完了などの「視聴資格」は期限付きの認可情報として配布する。期限切れ時は新規再生を許可しないが、運動機器自体を危険な方法で停止させない。
- **停止対象は原則動画の再生であり、モニターやApple TVのAC電源ではない。** 制御可能な専用プレイヤー/連携APIでPoCする。
- 利用者がいつでも運動を中断でき、緊急時に再生制御や警告を安全に停止できる。

**状態**: `IDLE` / `READY` / `PEDALING` / `WARNING` / `PAUSED` / `ENDED` / `FAULT`。  
**監視値**: RPM、検出パルス、連続運動秒数、停止秒数、センサー異常、最終通信時刻。

**物理安全**: 商用電源を扱う自作リレーを本プロジェクトの必須構成に含めない。将来使う場合も機器の適合性、定格、電気安全、メーカー制限を個別審査する。

### 6.3 家電・照明・空調

- 起床30分前の予熱は**メーカー公式のスケジュール機能/APIに対応したエアコン**等に限定する。
- 帰宅/就寝時は照明、対応する非必須機器のみを制御対象とする。
- 暖房器具、医療機器、通信機器、冷蔵庫等を「日次達成まで使わせない」対象にしない。
- 家電制御が失敗した場合も生活フェーズは進行できる。アプリには失敗を表示する。
- サーバー障害時の無人自動起動は禁止。メーカー側に安全な独立スケジュールがある場合のみ例外とする。

### 6.4 DNS/ネットワーク

- NextDNSの専用プロファイルを作り、娯楽ドメインの拒否リストをAPIで管理する。家族や仕事の端末と共有するDNSプロファイルは使用しない。
- `x.com`、`instagram.com`、`youtube.com`、`nicovideo.jp` 等は初期ブロック候補とし、実際の遮断対象は設定ファイルで管理する。
- `arxiv.org`、GitHub、大学サイト等を研究用の許可候補とする。ただし認証、CDN、GitHubの依存ドメイン等はテストで補完する。
- DNSフィルタは完全な通信遮断ではない。別DNS、VPN、DoH/DoT、既存コネクション、IP直打ち等の制限範囲を分けて記録する。
- 初期PoCでは**拒否リスト方式**を優先する。全許可リスト方式は業務・認証・生活必需通信への影響を検証してから導入する。
- 適用時刻を保証しない。設定反映までの時間と端末側キャッシュを測定し、管理画面には「要求済み/反映確認済み/失敗」を分けて表示する。
- 外部サービス障害時でも本人が利用する復旧手段（管理用ネットワーク設定/バックアップ接続）を事前に用意する。

### 6.5 macOS Agent

- **User LaunchAgent / Hammerspoon:** UI通知、エディタ起動、ウィンドウ配置、フォーカス画面起動、アプリ使用状況の観測を担当。
- **Privileged Helper（必要時のみ）:** OSの特権が必要な限定操作を担当。初期MVPに含めない。
- 禁止アプリ起動時はまず通知または通常の終了要求を行う。`SIGKILL` は既定で使用しない。
- 未保存データがあるアプリ、認証/会議/緊急連絡用アプリの強制終了を行わない。
- OS再起動後の復旧、Agent停止/更新、ポリシー期限切れ、ユーザーによる解除を考慮する。
- スリープ解除やWi-Fi接続はカーネルフックではなく、対応するOSイベント/APIから受け取る。
- macOSの画面ロック、ユーザー切替、画面共有、外部ディスプレイ接続時の挙動を実機で検証する。

### 6.6 iOS：NFC・ショートカット・MDM

- MVPのiPhone側要件は**ショートカットのNFCトリガー**と認証済みAPI連携。NFC利用のために監視対象モード/MDMを必須としない。
- ShortcutsのNFCトリガーはタグ固有識別子を用い、NDEF内容はトリガー判断に使わない。各タグの`tag_id`をショートカット設定に静的に対応づける。
- iPhoneの背景NDEF読み取りは通知→リンク遷移を要する場合がある。ロック、画面OFF、Wallet/カメラ等の条件で挙動が変わるため実機確認する。
- 将来専用iOSアプリを開発する場合、Core NFC / App Intents / Universal Linksを評価。PWAだけでOSレベルのNFC背景監視を実行できると仮定しない。
- iOSのSNS制限を強めるMDM導入は**独立した後期フェーズ**。監視対象化・非同期ポリシー反映・復旧手順を検証用端末で確認する。
- Safari等のブラウザを制限する場合、NDEF Web方式の到達経路や`/focus`利用が阻害されないか確認する。
- 緊急通話、連絡、認証、地図、決済、OS設定、本人の復旧経路は維持する。

### 6.7 PWA / UX

- 今日の生活フェーズ、最後に受理されたNFCチェックポイント、集中タイマー、次の推奨タグを表示する。
- **タグ台帳画面:** 用途・設置場所・登録先iPhone・有効状態・読み取り方式・最後の成功時刻・交換手順。
- タッチ結果は「チェックポイント受理」「状態変更なし」「遷移不可」「通信失敗」「デバイス適用待ち」を区別する。
- 現場でタグを読めない場合、同じ画面から**手動の状態確定・訂正**ができ、操作元を監査ログに残す。
- 翌日のTo-Doは3枠。研究時間、RPM、入浴/クロッキーの自己申告、誤タッチ、手動解除も表示する。
- すべての制限の「理由」「有効期限」「適用状態」「復旧方法」を表示する。
- 一時解除と緊急解除を分かりやすく表示し、PC側には**ネットワーク不要の解除経路**を残す。
- X総括投稿案/Intentを生成するが、本人確認前には外部公開しない。

### 7.2 一意性・整合性

- `nfc_tags.tag_id`はサーバー発行の不透明IDであり**タグの物理UIDではない**。用途が変わる場合はバージョンを上げて監査する。
- `nfc_scan_attempts.scan_id`はグローバル`UNIQUE`。同一スキャンの再送は保存済みの同じ判定を返す。
- `nfc_bindings(binding_id,device_id)`に一意制約を置き、無効なバインディングの利用を拒否する。
- `NFC_STRENGTH_SET`は`scan_id`に加えて**日次セッションのセット番号**で追跡する。同一タッチで複数セットを増やさないが、後続の正当なタッチは許可する。
- `state_snapshots.revision`は単調増加。状態更新をトランザクション直列化し、ポリシー配布は同revisionに紐付ける。
- タグの`DISABLED`/`REPLACED`を反映する際、過去のイベントや当時の記録を変更しない。
- `occurred_at`と`received_at`を区別する。時刻異常/古いイベントは監査保存のみで遷移を拒否する場合がある。
- NFCの固有識別子や読み取り位置等の過剰な個人データを収集しない。原則として必要なのは**登録済み論理タグIDとアクション結果**。

### 7.3 保持方針（初期案）

- スキャン試行と制御監査ログ：原則90日。日次集計は任意の長期保存。
- 高頻度のRPM生データ：原則7日。セッション集計は長期保存。
- タグ失効・交換履歴：現役の行動ルールに影響する期間保存し、古い詳細ログは削除可能にする。
- 投稿文案/自由記述/行動記録は本人による削除を可能にする。
- 保持期間は暫定値。プライバシーと運用負担に応じて調整する。

## 8. API・イベント契約

### 8.1 認証・通信・共通ルール

- PWA/管理画面は本人認証済みセッション（CSRF対策を含む）を使用する。
- Shortcutsは**端末単位・NFCイベント投稿のみ許すスコープ付き資格情報**でHTTPSの`POST`を行う。長期の全権管理者トークンをショートカットやタグURLに埋め込まない。
- 端末資格情報は失効・再発行可能にする。端末紛失時は対象`nfc_bindings`を停止する。
- `scan_id`はタッチごとに生成するUUID。ネットワーク再送では同じ`scan_id`を使う。
- タグIDやURLがコピーされる前提で、認証・状態遷移許可・レート制限・監査により保護する。**タッチの物理的真正性まで保証しない**。
- APIエラーは`401/403`（認証/許可なし）、`404`（未知のタグ）、`409`（状態矛盾/重複）、`422`（不正入力）、`429`（連続操作制限）、`503`（一時不可）等を使い分ける。
- 同一`scan_id`の正常な再送は**元の判定を返す**（その再送自体をエラー扱いしなくてもよい）。
- スキャン受理と外部デバイスへの適用完了は異なる。`device_commands`のACKを別に確認する。

### 8.2 NFCタグの登録・管理

| Method | Path | 用途 |
|---|---|---|
| `POST` | `/api/v1/nfc/tags` | 論理タグの作成と用途割当て |
| `GET` | `/api/v1/nfc/tags` | タグ台帳と接続状態の一覧 |
| `GET` | `/api/v1/nfc/tags/{tag_id}` | 登録・有効状態・設置場所の取得 |
| `PATCH` | `/api/v1/nfc/tags/{tag_id}` | ラベル/設置/用途の変更（履歴つき） |
| `POST` | `/api/v1/nfc/tags/{tag_id}/disable` | 紛失・退役タグの失効 |
| `POST` | `/api/v1/nfc/tags/{tag_id}/replace` | 新しいID発行・旧タグの無効化 |
| `POST` | `/api/v1/nfc/bindings` | iPhoneのオートメーション/タグとの紐付け |
| `DELETE` | `/api/v1/nfc/bindings/{binding_id}` | 紐付け停止 |

タグ登録/停止/交換は管理者権限が必要で、**タッチ受付用の端末資格情報には付与しない**。

### 8.3 NFCタッチ受付

`POST /api/v1/nfc/scans` （Shortcutsまたは本人確認後のWeb操作）

```http
POST /api/v1/nfc/scans
Content-Type: application/json
Authorization: Bearer <device-scoped-token>
```

```json
{
  "scan_id": "13bd299d-bb93-4dbd-bfd6-8a747eb3f2b1",
  "tag_id": "nfc_7d41c2a09c1e4c90",

  "source": "IOS_SHORTCUTS",
  "occurred_at": "2026-11-17T09:00:00+09:00"
```

サーバーは`tag_id`→有効なタグ→`purpose`→現在状態の許可遷移へ解決する。リクエスト本文に任意の`action=UNLOCK_ALL`等を受け入れない。

**受理応答例（200）**

```json
{
  "scan_id": "13bd299d-bb93-4dbd-bfd6-8a747eb3f2b1",
  "checkpoint": "NFC_LAB_ARRIVAL",
  "outcome": "ACCEPTED",
  "state_changed": true,
  "state_revision": 43,
  "policy_status": "DISPATCH_PENDING",

```

**拒否応答例（409）**

```json
{
  "scan_id": "13bd299d-bb93-4dbd-bfd6-8a747eb3f2b1",
  "outcome": "REJECTED",
  "reason": "INVALID_TRANSITION",
  "message": "この操作は現在の生活フェーズでは実行できません。"
}
```

**モードB（NDEF URL）:** `GET /tap/{tag_id}`では説明・現状・確認ボタンだけを返す。**GETからAPIへの自動POSTをしない**。ログイン済みユーザーがボタンを押した後、CSRF対策済みの同じAPIへ`source=NDEF_WEB`で送信する。短縮URLの先読みやQRでのアクセスでも勝手に状態を変えない。

## 9. 障害時・例外時の設計

### 9.1 Fail-safeマトリクス

| 障害 | 期待される動作 | 復旧経路 |
|---|---|---|
| タグが読めない/紛失 | 操作不可を表示。**ルーティンを継続可能** | PWA手動操作、旧タグ停止と交換 |
| タグの誤貼付・混同 | 受理前/後に用途と結果を表示。相反する遷移を拒否 | 台帳の修正、過去イベント訂正 |
| タグが複製/URLが転載 | タグだけでは認証成立しない。異常アクセスを監査 | `tag_id`停止、登録し直し、資格情報失効 |
| iPhoneがロック中/バッテリー切れ | 自動実行を保証しない | 端末復旧、PWA手動操作、別端末の認証済み操作 |
| Shortcuts権限不足/自動実行失敗 | 成功扱いせず、エラー/未受信を確認 | Shortcuts設定確認、NDEF Web方式 |
| NFCタッチの二重送信 | 同じ`scan_id`は1回のみ処理 | 再送は元の応答を取得 |
| 連続した異なるタッチ | リバウンド抑止、正当な筋トレセットは別々に記録 | 結果表示と訂正 |
| NFC送信後に通信断 | 応答未取得を成功とみなさない | 同じ`scan_id`で再試行、状態取得で確認 |
| 古いスキャンの遅延到着 | 現在状態を巻き戻さない | 拒否理由表示と手動補正 |
| バックエンド停止 | 期限切れのPC制限は安全に縮退、タグイベントを未確認表示 | PCローカル解除/サーバー復帰 |
| DNS更新失敗 | 適用失敗を表示、必要な接続を確保 | DNS設定のローカル復旧 |
| macOS Agent停止 | OS操作を不能にしない | Agent再起動/ローカル解除 |
| ESP32通信断 | RPM計測・停止判定はローカル継続 | 再接続、手動で運動停止 |
| ESP32センサー異常 | FAULTを表示、再生制御を安全側へ | センサー点検、運動中断 |
| MDMの反映遅延 | 未適用を明示して即時性を保証しない | 検証用端末で復旧手順確認 |
| 体調不良・緊急外出 | 休養/例外を正規フローとして処理 | `TEMPORARY` / `EMERGENCY` |

### 9.2 緊急解除

- インターネットが使えなくてもmacOSの習慣化制限を解除できる**NFC非依存のローカル手段**を必須とする。
- PWAの解除は現状と有効範囲を説明し、長い理由入力や複雑なトークン入力を要求しない。
- 緊急解除は筋トレ3セット、25分集中、タグタッチなどを要件にしない。
- 電気安全やOS保護の解除は対象外。解除の成功/失敗を監査する。

### 9.3 保護対象

緊急通話、医療、防災、生活上必要な連絡、交通、本人確認/認証、仕事上必須の通信、データ保存、OSの復旧機構、休養する自由を一律の遮断対象にしない。

## 10. 非機能要件（NFR）

| ID | 要件 | 初期受け入れ基準案 |
|---|---|---|
| NFR-01 | NFCスキャン冪等性 | 同じ`scan_id`100回再送しても同じ判定で状態変化1回 |
| NFR-02 | NFC受付応答 | 通常オンラインでサーバー到着後の処理p95 2秒以内を目標（OSのNFC検出時間は別集計） |
| NFR-03 | PC制御反映 | オンライン時、ポリシー変更から端末ACKまでp95 10秒以内を目標に計測 |
| NFR-04 | NFC読み取り品質 | 主要タグ・主要利用状態の各方式で100回程度試験。通常条件のトリガー→受付成功率95%以上を**採用目標**とし実測レポート |
| NFR-05 | iOS制約の可視化 | 画面ON/ロック/復帰直後/カメラ/Wallet/オフラインのケースを記録し、未受信を成功と誤認しない |
| NFR-06 | タグ管理 | 失効したタグへの新規スキャン100%拒否、旧ログ維持、交換が管理画面から可能 |
| NFR-07 | 複製・URL対策 | 無認証のGETやコピーURLから状態変更なし、無認証POSTは拒否 |
| NFR-08 | 正当な連続操作 | 同一スキャンの再送で筋トレは1件のみ加算。新たなセットの独立したタッチは条件付きで加算 |
| NFR-09 | オフライン復旧 | サーバー・通信・NFCがなくてもPCの習慣化制限を解除可能 |
| NFR-10 | バイク停止判定 | 通信断でも5秒警告・10秒停止のローカル判定が継続 |
| NFR-11 | セキュリティ | 端末資格情報の失効、タスクごとの権限分離、CSRF対策、操作監査がある |
| NFR-12 | データ整合性 | 古いイベントでは状態が巻き戻らず、適用成功はACK確認後に表示 |
| NFR-13 | プライバシー | NFC履歴/行動データを期限管理し、本人が削除できる |
| NFR-14 | 安全性 | 必需通信や危険な機器の自動通電/遮断を要件に含めない |
| NFR-15 | MDM互換性 | 端末/OS/製品別に可用機能・反映遅延・復旧手順をPoC記録（MVPのSLA対象外） |

**補足:** 成功率95%と応答時間は開発時に検証する**目標値**であり、Appleの保証ではない。ショートカット起動時間、API実行時間、端末制御ACKを別々に計測する。

| AT-019 | 無効化/交換されたタグで送信 | 拒否され旧ログは保持される |
| AT-020 | 他端末・無認証でタッチAPI送信 | 拒否し、秘密情報を漏らさない |
| AT-021 | iPhoneがオフラインでタッチ | 未受信を成功と誤表示しない。手動補正可能 |
| AT-022 | 古いNFCイベントを後から送信 | 現在の生活フェーズが巻き戻らない |
| AT-023 | NFCタグもネットも使えない状態でPC解除 | オフライン緊急解除できる |
| AT-024 | タグの貼替・再登録・端末変更 | 新しい登録を利用でき、古い紐付けは無効化 |
| AT-025 | MDM配布が遅れる | タッチ受理済みでも端末制限は「未反映」と表示 |
| AT-026 | X投稿案を含めて日次クローズ | 文案を生成するが無確認投稿はしない |
| AT-027 | 休養日/体調不良を選ぶ | タッチ済みでも運動を強制せず通常の生活利用を維持 |

## 12. 開発ロードマップと完了条件

### Phase 0：NFCイベント契約・状態モデルのPoC

**Exit:** AT-001、AT-002、AT-003、AT-005、AT-018、AT-019、AT-020、AT-021、AT-024合格。NFR-04の測定報告。

### Phase 2：macOS Agent・DNSとNFCトリガーの統合

- 研究室タグ受理→エディタと`/focus`起動、適用結果ACK、DNSの制限反映を接続する。
- `NFC_FOCUS_START`→集中25分→15分解放権→90分ごとの休憩を統合する。
- 期限付きポリシー、オフライン解除、DNS失敗復旧手順を整える。

**Exit:** AT-005〜009、AT-023合格。外部DNSの反映遅延は実測値として記録。

### Phase 3：筋トレ・ESP32バイク・日次クローズ

- 筋トレセット、バイク開始、入浴、クロッキー、日次クローズのタグを追加する。
- ESP32の回転計測と5秒/10秒のローカル判定を実装し、動画再生の一時停止へ接続する。
- 日次To-Do・レビュー・ヒートマップ・X投稿案を統合する。

**Exit:** AT-010〜017、AT-026、AT-027合格。AC電源のDIY遮断は行わない。

### Phase 4：iOSの強い制限（任意・独立）

- NFC操作の結果を使うMDM側のアプリ許可/拒否を検証用端末で試す。
- NFC/ShortcutsとMDM配布の非同期性、Safari/PWAへのアクセス維持、端末復旧を確認する。
- 運用負担に見合わなければ採用しない。

**Exit:** 機種・OS・MDM別の適合表、採否ADRを作成。

### Phase 5：運用データから改善

- タッチ忘れ、遷移拒否、制御適用遅延、手動解除を週次分析する。
- タグ配置や数を整理し、行動の煩雑さを軽減する。
- ルール変更の前後で集中開始遅延や達成率を比較する。

**Exit:** 無理のない継続運用と復旧可能性を実測で確認。

## 15. 用語集

- **NFC Checkpoint:** 本人がタグにスマートフォンを近づけ、特定の行動を申告する操作点。
- **NFC Tag / `tag_id`:** 生活空間に設置する物理タグ / サーバーが発行する公開の論理タグ識別子。タグの固有UIDは認証秘密ではない。
- **NFC Binding:** iOSショートカット・NDEF Web・専用アプリとサーバー上のタグ用途の紐付け。
- **Shortcuts NFC Trigger:** タグの固有識別子を使って個人用オートメーションを起動するiOS機能。タグ内のNDEF内容はトリガーに使用しない。
- **NDEF URI:** NFCタグに記録するURL形式のデータ。背景読み取り後にWebページ等へ誘導できる。
- **Scan Attempt:** タッチイベントの受付試行。処理済み・拒否・重複・応答不能を区別する。
- **Self-declared Action:** タグをかざして本人が行ったと申告した行動。位置・運動・完了の物理証明ではない。
- **State Reducer:** イベントから状態を確定してrevisionを更新するコンポーネント。
- **Policy Engine:** 状態・安全ルール・解除モードから制御方針を計算する仕組み。
- **Device Adapter:** macOS、DNS、MDM、ESP32、家電などにポリシーを適用するコンポーネント。
- **ACK:** デバイスが制御を適用した成功/失敗結果。NFC受理とは別。
- **Fail-safe / Emergency Override:** 故障時の安全な縮退 / タグなしでも利用できる緊急解除。
- **MVP:** 初期継続運用できる最小構成。本版ではNFC 3枚・iPhone・PWA・状態管理から始める。

## 付録A. 実装の推奨順序（最小の縦断スライス）

1. サーバーの`nfc_tags`に`NFC_WAKE`、`NFC_DEPARTURE`、`NFC_LAB_ARRIVAL`用のタグを作成する。
2. iPhoneショートカットで3枚を別々に登録し、各NFCトリガーから専用`tag_id`と新規`scan_id`を送信する。
3. `NFC_WAKE`を受理→`MORNING`→45分計測開始。
4. `NFC_DEPARTURE`を受理→`TRANSIT`→45分出発判定。
5. `NFC_LAB_ARRIVAL`を受理→`RESEARCH`→`/focus`とエディタの起動要求。
6. 25分集中の実計測完了で15分解放権を発行し、有効期限到達で失効させる。
7. タグを無効化/貼替、通信断、再送、手動補正、オフラインPC解除を試す。
8. 同一スキャンと別のスキャンの違い、ACK前後の違いを監査画面から確認する。

**この縦断スライスを完成させるまでは、iOS MDM、rootデーモン、ACリレー、タグの大量設置を追加しない。**

## 付録C. v2.0からの移行・互換性

- **削除する概念:** `BEACON_ENTERED`/`BEACON_EXITED`、`NODE_WASHROOM`/`NODE_ENTRANCE`/`NODE_LAB_DESK`等のビーコン観測ノード、RSSI、iBeacon UUID/major/minor、近接の自動推定、IRK依存、BLEのPhase 3。
- **新設する概念:** `NFC_SCAN_RECEIVED`、`NFC_CHECKPOINT_ACCEPTED/REJECTED`、`nfc_tags`、`nfc_bindings`、`nfc_scan_attempts`、Shortcuts/NDEF Web Bridge。
- **維持する概念:** `SystemState`の直交状態、Policy Engine、macOS Agent、DNS Adapter、ESP32、MDM任意PoC、期限付きポリシー、オフライン解除、監査ログ。
- **既存ログの扱い:** v2.0までのBLEイベントが存在する場合は履歴として残すが、新版のNFC状態遷移へ再投入しない。新規イベントは`source`/`schema_version`で区別する。
- **移行の最重要ポイント:** 「センサーが近接を観測した可能性」から「本人がチェックポイントを意図的に操作した」という意味へ変更する。ただしタッチは物理的な行動完了の証明ではない。
